What went wrong — and what we're doing about it

Specs were readable by machines, not people
→ One-pager per OS + NotebookLM
"Specs are difficult to read. Good for LLM but not for humans. Human readable PRD must be derived with diagrams from these Specs."
Marut
"While OS docs absolutely need to remain LLM-readable for agentic builds and scalable codegen workflows, there also needs to be a strong layer of human readability and experience articulation — visuals, workflows, flowcharts, journey representations."
Mukul
"Complete the OS asap and make it machine as well as Human readable before any development starts."
Ashish
"Assuming that we dont need to understand OS and their workflows [was the mistake]."
Marut
What we're doing: One plain-language one-pager per OS (all 8 done). NotebookLM loaded with all specs, one-pagers, and registries — anyone can ask any question at any time. This alignment week (29 May–5 June) is entirely built around the team reading the OS in human-readable form before a line is written.
Experience layer not locked before build started
→ Phase 2: Experience Lock (June 6–10)
"There should ideally be an explicit stage where the experience layer gets locked alongside the specs before downstream implementation begins. This can significantly improve alignment, reduce iteration loops, and improve overall build efficiency."
Mukul
"Too many to and fro with design team. How they name the controls will impact binding with backend at later stage."
Marut
"Design Handoff will take time and digress if scope not defined clearly."
Marut
"What are the workflows and how they are going to get impacted with the Customer OS in place? Rank them in order of impact and pick them accordingly."
Ashish
"Codebase and how BE and FE interacts with each other in technical terms [is what I wish I had known earlier]."
Ashish
What we're doing: June 6–10 is a dedicated Experience Lock phase — Ashish produces and locks flows, UI, and journey maps for all 8 OSes before any code is written. Terminology alignment session (Wed 3 June) locks spec vocabulary to design vocabulary. Design/BE-FE walkthrough with Marut before Ashish produces any screens. Workflow impact ranking done before Phase 3 — build sequence respects that order.
Build sequence never locked — no atomic deliverables
→ Atomic units defined, sequence locked by June 10
"Sequence of OS implementation was not clear so prompts had to run multiple times."
Marut
"Project Management — Deliverable as atomic unit must be defined."
Marut
"Avoid creating end to end at one time. Should pick development of it in small chunks. We may take everything live at once [but build incrementally]."
Ashish
"Build first draft as soon as possible to know drawbacks of Process and Specs."
Devender
What we're doing: Atomic deliverables defined per OS with Marut sign-off before June 10. Build sequence locked by June 10 — B2I → SQ → Recovery → Continuity → RS → Exit → CM → ARR. Small-chunk build enforced by atomic units: ship incrementally even if go-live is combined. Debug panel built from Phase 3 day one so every chunk is verifiable.
Migration and data treatment never planned
→ Migration decided before build starts
"We should have known entire universe of specs and their role. Migration should be decided before hand."
Marut
"Old → new data treatment approach principles [is what I wish I had known earlier]."
Dhruv
"Should have asked more questions on Migration. In my view this should be simpler because ideally there should be no app or offering change. Migration of the customers to new OS should be clean."
Nishit
What we're doing: Migration is a Phase 2 deliverable — three decisions locked before a single line is written: (1) migration approach (backend-only or surface change), (2) old→new data treatment principles, (3) integration blast radius. Dedicated working session Thu 4 June: Dhruv + Marut + Nishit.
Integration blast radius and in-flight projects not assessed
→ Mapped by June 10
"Need to figure out integration interfaces between CSP ↔ Customer/Ops (CX portal, ticketing) / Other (captive portal) systems — larger blast radius to BAU. Also current in-flight projects priorities in advance of starting build."
Dhruv
"Incorporating inputs from user facing workflows / existing data structure to inform governing decisions / tech architecture decisions in advance — front load decisions pre execution."
Dhruv
What we're doing: Integration interface map (CSP ↔ Customer OS ↔ Kapture ↔ captive portal) produced by June 10 — Dhruv + Marut. In-flight project inventory done by June 10 — Dhruv. Neither is optional: both are G3 gate criteria.
OS dependencies and internals not understood early enough
→ OS dependency matrix + wiring guide before Phase 3
"Not Understanding the OS internal working [was the main pain]."
Devender
"We need ES or Workflow as well to use OS in App [— wish had this before build]."
Devender
"Dependency of OS must workout as soon as we come to know. Should not defer."
Devender
"Clearly articulate in spec dependency matrix and external parameters."
Marut
What we're doing: OS dependency matrix produced before Phase 3 (Item 14). Wiring guide per OS — how states and events map to app behaviour — produced in Phase 2 by Adit + Marut. Cross-OS walkthrough exercise (Satyam's framework) verifies every seam before build starts. Sessions 3–7 this week are specifically to ensure Marut, Devender, Ashish understand OS internals before any code is written.
Amendment process too confusing
→ Varun-led session, Wed 3 June
"Spec Amendment process is very confusing. It will impact the build if it can't be stitched together."
Marut
What we're doing: Dedicated amendment process session Wednesday 3 June, led by Varun. Every person leaves knowing exactly: what an amendment is, when to raise one, how it's reviewed, what's blocked without it. One session before build, not discovered mid-sprint.
Business impact never tied to the OS
→ Metrics validated with Nishit by June 5
"Impact to overall metrics is not called out. Too much time creating and making it live [without knowing what it was moving]."
Nishit
What we're doing: Business impact metrics drafted for each OS (RDNI rate, support contact rate, compensation consistency, pickup SLA, AT_RISK detection window, repeat complaint rate). Validated by Nishit + Dhruv before June 5. Every OS in the build is tied to a metric it's supposed to move.
